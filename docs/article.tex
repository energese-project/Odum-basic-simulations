\begin{abstract}
H.T. Odum and his colleagues published many of their ecological simulation models as BASIC listings: short numbered programs, printed beside an Energy Systems Language diagram, meant to be typed in and run. The machines they were written for are gone, and the listings survive only on paper, so the models can be read but are rarely run, checked or extended. We present Odum BASIC Simulations, an open archive and browser workbench in which these listings run unaltered. A BASIC interpreter written for the purpose runs in the browser; the table a program prints is recovered and plotted, and the printed output stays visible beside the plot. Every program is stored with a machine-checked provenance record: a citation in BibLaTeX form, a declared fidelity to the published listing (verbatim, corrected, adapted or original) and, where available, the program's diagram with the rights under which it is reproduced. The build refuses any program whose record is incomplete. Programs can be contributed as a pull request, through a GitHub issue form processed by an automated workflow, from an in-browser workspace that fills in that form, or by labelling an issue for a coding agent, which transcribes the source into archive files for human review. The software itself was built largely by an LLM coding agent working under human direction, test-first, against written repository standards, with every change reviewed and merged by a person; we describe that process, its controls and the failures they caught. For three mini-models, the interpreter reproduces each listing's own Euler arithmetic on every printed row to within the rounding of its number format ($5\times10^{-7}$), and a comparison with the exact solutions exposed a timing error in one of the archive's own worked examples. The archive is openly available at \url{https://energese-project.github.io/Odum-basic-simulations/}.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Howard T. Odum and his colleagues did not only describe their models of ecological and economic systems; they printed them. Across the teaching and research books of the 1980s and 1990s a model is typically given twice, once as an Energy Systems Language diagram and once as a short BASIC listing that implements it \citep{odum1983,odumMinimodels,odumOdum2000} \verify{} (count the listings per book before stating a number). The listing was meant to be used. A student could type it into a microcomputer, run it, change a coefficient and run it again, and in doing so learn what the diagram meant as a set of differential equations. Few forms of publication in ecology are as concrete: the model is not described in prose and left for the reader to reconstruct, it is handed over whole, in a form that can be executed.

That form has not aged well. The machines the listings were written for are museum pieces, the dialects of BASIC they used have drifted apart and then out of use, and no current operating system ships an interpreter for any of them. A listing on paper is now a model that cannot be run, and a model that cannot be run cannot be checked against its own claims, compared with another model, or reused as the starting point for a new one. Retyping a listing into a modern language is possible, but it produces a new program whose relationship to the published one is unrecorded: every translation decision and every typing error is silent. This is the general problem that \citet{hinsen2019} calls software collapse, in an unusually pure form. The code survived, on paper, in full; everything it depended on did not.

This paper presents Odum BASIC Simulations, an open archive and browser workbench built to reverse that loss. It makes four contributions. First, an interpreter, written for the purpose, runs the published listings as printed, and recovers a plot from the numbers they print, so that nothing has to be rewritten for a listing to be run and seen. Second, an archive in which each program's provenance is a machine-checked record rather than a comment: where the listing came from, how faithful it is to the page, and on what basis its diagram is reproduced. The build refuses a program whose record is incomplete. Third, four contribution routes, from a pull request to an in-browser workspace, designed so that someone with the book and no programming background can add a program without lowering the bar it must pass. Fourth, an account of how the software was built, largely by a large language model (LLM) coding agent working under human direction, with the controls that were used and the failures they caught, and of how a second agent can serve as a transcription route.

Section~\ref{sec:background} places the work in the history of simulation in Odum's systems ecology and in current practice for research software. Section~\ref{sec:design} states the design principles and the decisions each one forced, and Section~\ref{sec:implementation} describes the interpreter, the workbench and the archive. Section~\ref{sec:contributing} describes the contribution routes, Section~\ref{sec:llm} the use of an LLM coding agent as method, and Section~\ref{sec:validation} the validation. Section~\ref{sec:discussion} discusses what the archive makes possible and where it falls short.

\section{Background: simulation in Odum's systems ecology}
\label{sec:background}

\paragraph{From circuits to code.} Odum's energy circuit language began as an analogy with electrical circuits, in which storages behave like capacitors and flows like currents driven by a potential \citep{odum1960}. Over the following decades it became a general notation for systems of any kind, with symbols for sources, storages, interactions, producers, consumers and heat sinks that carry definite dynamical meaning \citep{odum1972,odum1983,odum1994}. Simulation was part of the notation from the start. A diagram specifies a set of differential equations, one per storage, and those equations were run: first on analogue computers, patched together to mirror the diagram, and later as programs on the microcomputers that reached teaching laboratories in the 1980s. The language itself, and the problem of drawing it reproducibly, are the subject of the companion \texttt{energese} paper \verify{} (cite once it has a DOI); this paper is concerned with running the models.

\paragraph{BASIC as the teaching medium.} BASIC was designed at Dartmouth for students who were not programmers \citep{kemenyKurtz1964}, and by the 1980s some dialect of it was built into almost every microcomputer a student could reach. That made it the natural language for a listing printed in a book: short enough to type in an afternoon, and runnable without a compiler. The listings share a recognisable shape. Coefficients and initial storages are set with \texttt{LET}; a \texttt{FOR} loop advances time in steps of \texttt{DT}; inside it each flow is computed from the current storages and each storage is updated by forward Euler integration; and a \texttt{PRINT} statement emits one row of a table per step, or, in the later material, screen graphics plot the trajectories as they are computed. Listing~\ref{lst:shape} shows the shape, taken from a worked example in the archive. Two families of dialect appear in the sources: Commodore-era BASIC V2 in the earlier material, and GW-BASIC or QuickBASIC, with \texttt{SCREEN}, \texttt{PSET} and \texttt{LINE}, in the later \verify{} (confirm per book).

\paragraph{What exists today.} Two kinds of tool come close, and neither is enough. Emulators of the original machines can run a listing, but they need ROM images that cannot be redistributed, and they run the machine rather than the model: the listing still has to be typed in, the output still scrolls past on an emulated screen, and nothing records where the listing came from. General system-dynamics environments such as Stella, Vensim and Insight Maker \verify{} (cite each properly) can express the same models, often more conveniently, but only by re-expressing them; the published artefact itself is never run, so it is never checked. Re-implementations of individual Odum models exist in the literature \verify{} (search; cite any found), but each stands alone, and none keeps the published listing as the thing that runs. What is missing is an archive in which the listings themselves run, with their provenance attached.

\paragraph{Provenance and research software.} The FAIR principles, first stated for data \citep{wilkinson2016} and since adapted for research software \citep{barker2022}, ask that software be findable, accessible, interoperable and reusable, and the software citation principles ask that it be cited as a first-class research output \citep{smith2016}. Both apply here, and the archive is designed to meet them: every program has a stable URL, a machine-readable record and a citation. But an archive of transcriptions raises a question those frameworks do not name, because they assume the software in question is the original. We call it \emph{fidelity}: how close the executable artefact is to the published one. A program that has been corrected, modernised or rewritten may be exactly as findable and as reusable as a verbatim transcription, and still mean something quite different as evidence of what was published.

\section{Design principles}
\label{sec:design}

Four principles shaped the archive. Each is stated with the decision it forced, because a principle that forced nothing is decoration. This section is the paper's argument about how such an archive should be built; Section~\ref{sec:implementation} describes how this one was.

\paragraph{The listing is the product.} When a published listing and the interpreter disagree, the interpreter changes. The alternative, editing listings until they run, would make every archived program a derivative whose differences from the page have to be tracked and trusted. Three decisions follow. Listings are not rewritten into a modern language. Plots are recovered from the text a program prints (Section~\ref{sec:implementation}), rather than by requiring an output convention that no published listing follows. And a statement the interpreter does not yet support is a gap in the interpreter, recorded as work to do, not a reason to edit the source.

\paragraph{Provenance is data, and incomplete provenance is a build failure.} A listing whose origin cannot be read looks authoritative and is not. So every program carries a structured record, and the site does not build if any record is missing a required field or is inconsistent. The central field is \emph{fidelity} (Table~\ref{tab:fidelity}), with four levels from \texttt{verbatim} to \texttt{original}. It has no default, because it changes what every other field means: a \texttt{verbatim} listing's errors are the book's, an \texttt{adapted} listing's are the adapter's. Fidelity is also the one field that no automated route may set. A person chooses it, having compared the listing with the page.

\paragraph{Built to outlive its authors.} The archive's value is realised over decades, long after any maintainer has moved on \citep{hinsen2019}. It is therefore a static site with no server, no database and no account system: a directory of files that any web server can host. It uses the browser platform first, with Web Components rather than a framework, and has exactly two runtime dependencies, the Monaco editor and the Chart.js plotting library, both bundled into the site rather than fetched from a content-delivery network at run time, so that the site keeps working for as long as its files exist. Build and test tooling is exempt from this rule because none of it ships: if the build tools disappeared, the built site would still run.

\paragraph{Test first, from the outside.} Every change begins with a failing test. The tests are written against behaviour a user could observe, not against internal methods: interpreter tests run a BASIC listing and assert on what it printed, and archive tests are phrased as the mistakes a contributor could make, such as a missing citation or an undeclared image. Tests written this way survive a rewrite of the implementation, which matters here for a second reason. In Section~\ref{sec:llm} they are the main check on an implementation that the human author directed and reviewed but did not write line by line.

\section{Implementation}
\label{sec:implementation}

This section describes the software at the level a modeller needs in order to trust it and use it. Everything else is in the repository, which the paper cites.

\paragraph{The interpreter.} The interpreter is about 800 lines of TypeScript, written from scratch for this purpose: it emulates no processor and needs no ROM image, so it can be redistributed with the archive. It implements the Commodore BASIC V2 core that the listings rely on: \texttt{PRINT} with its comma and semicolon separators, \texttt{LET} (with the keyword optional), numeric and string variables, one- and two-dimensional arrays with \texttt{DIM}, \texttt{FOR}/\texttt{TO}/\texttt{STEP}/\texttt{NEXT}, \texttt{IF}/\texttt{THEN} with a line number or a statement, \texttt{GOTO}, \texttt{GOSUB}/\texttt{RETURN}, \texttt{INPUT}, \texttt{DATA}/\texttt{READ}/\texttt{RESTORE}, \texttt{REM}, \texttt{END}, \texttt{STOP}, several statements per line separated by colons, and the numeric and string functions including \texttt{EXP}, \texttt{LOG}, \texttt{SQR}, \texttt{INT} and \texttt{RND}. The graphics and structured-control statements of the later GW-BASIC and QuickBASIC listings (\texttt{SCREEN}, \texttt{PSET}, \texttt{LINE}, \texttt{WHILE}/\texttt{WEND}, \texttt{DEF FN}, \texttt{ON}\ldots\texttt{GOTO}, \texttt{PRINT USING}) are not yet implemented. The editor highlights them in a separate style rather than as errors, so a listing that uses them reads as code waiting for the interpreter, which is what it is. Arithmetic is in IEEE-754 double precision, and \texttt{PRINT} rounds a number to six decimal places. The original machines used shorter floating-point formats and printed a different number of digits \verify{} (Commodore BASIC V2: five-byte floats, nine significant digits), so a faithful interpreter reproduces a listing's model and arithmetic, not necessarily the last printed digit of the original run (Section~\ref{sec:validation}). The interpreter runs in a Web Worker, so a runaway program can be stopped without freezing the page. It knows nothing of the page: its only contact with the outside world is a set of callbacks for output and input, which is why the same code runs in the browser and under the unit tests.

\paragraph{Recovering the plot from printed text.} Because the listings print tables rather than write data files, the plot is recovered from their output. The rule is exact and deliberately simple. A line is numeric if it has at least two fields, separated by tabs or spaces, and every field parses as a finite number. A run of consecutive numeric lines with the same number of fields is a table, and a change of width ends it; the longest table in the output is the one plotted. Its first column is the independent variable and each further column is a series. If the nearest non-blank line above the table has the same number of fields and is not numeric, it supplies the column names, which is the shape a \texttt{PRINT "T", "Q"} before the loop produces; otherwise the columns are numbered. This is a heuristic on purpose. Requiring an output convention would mean rewriting the published programs, which the first principle forbids, and when the heuristic finds nothing the program's output is still shown in full. The plot has one y axis, never two, so that no series can be made to look like another by rescaling, and the printed output always stays visible beside the chart: the plot is never the only reading of a run. The recovered table can be downloaded as CSV.

\paragraph{The workbench.} Figure~\ref{fig:workbench} shows the workbench with the first mini-model after a run. A thin top bar holds the program picker and the run controls. The sidebar holds the explorer, which lists the archive and the reader's own programs with the fidelity of each, and the details of the selected program: its description, fidelity and what that means, its citation with a BibLaTeX export, and the rights under which its diagram is shown. The listing is in the editor; the diagram, the recovered plot and the printed output are beside it. Each program has a stable address (\texttt{?prg=} followed by its identifier), so a paper or a lecture can link to a model ready to run.

\paragraph{The archive.} The archive is one directory, \texttt{programs/}, holding two files per program and optionally a third: the listing (\texttt{.bas}), a metadata sidecar (\texttt{.json}, Listing~\ref{lst:sidecar}), and a diagram image. There is no manifest to keep in step: the build finds the files, validates every sidecar with the same functions the contribution routes use (\texttt{parseProgramMeta} for one record, \texttt{readCatalog} for the whole directory), and fails with a message naming the file and the field if any record is incomplete or inconsistent. The raw files are published beside the site at stable URLs, so that a citation can point at the listing itself rather than at a page that displays it, and the end-to-end tests check that every published listing is identical to the one the workbench runs.

\paragraph{Diagrams and rights.} The diagram is the other half of what Odum published, and usually the easier half to check a model against (Figure~\ref{fig:minimodel}). A diagram is archived only with its rights recorded (Table~\ref{tab:rights}): a basis, which like fidelity has no default, a written statement, and for anything not drawn for the archive a source and, where it applies, the figure and page. The build rejects an image that no sidecar declares, an image whose content does not match its file extension, and any image over 2~MB. SVG is refused outright, because an SVG opened directly from the site can run scripts. The argument for recording rights per figure is in Section~\ref{sec:discussion}.

\section{Contributing programs}
\label{sec:contributing}

The archive grows only if people who own the books can add to them, and most of those people are ecologists, not programmers. There are therefore four routes in, in order of decreasing technical demand (Table~\ref{tab:routes}, Figure~\ref{fig:routes}). The point of the design is that every route ends in the same validator and the same human review, so that lowering the barrier to contributing does not lower the bar a contribution must clear.

\paragraph{A pull request.} A contributor who uses git adds the two or three files and opens a pull request. Continuous integration builds the catalogue, which validates every sidecar, and runs the full test suite; a maintainer reviews and merges.

\paragraph{A GitHub issue form.} A contributor with a GitHub account and no knowledge of git or JSON opens an ``Add a program'' issue, pastes the listing, types the citation into labelled fields, chooses the fidelity and, if there is a diagram, drags the image in. A workflow parses the issue, builds the files, and checks the whole archive with the build's own validator. If anything is wrong it comments on the issue with every problem at once, in the form's own words; editing the issue runs it again. When everything passes it opens a pull request that credits the contributor as co-author, and runs the full test suite on it. Two security properties matter, because the issue text is written by anyone. The issue text is never passed to a shell: it is read from the event payload by a script, and the only part of the issue that reaches a shell command is its number. And a diagram is downloaded only from GitHub's own attachment hosts, so the workflow cannot be made to fetch an arbitrary URL. A photograph of the source page can be attached for the reviewer; it stays in the issue and is not published, so a page image is never redistributed from the archive.

\paragraph{The in-browser workspace.} A contributor can also write a program in the workbench itself. ``My programs'' is a private area of the browser's own storage, the Origin Private File System, in which a program can be written, run and described, with the details panel acting as a form that is checked against the build's rules as the contributor types (Figure~\ref{fig:workspace}). \emph{Submit} then opens the issue form above, already filled in, so the workspace is a friendlier front end to the second route rather than a separate one. Two design decisions are worth stating. The archive itself is never copied into the workspace as a whole, because a copy would go stale when an entry is corrected upstream. And an individual archive program copied into the workspace loses its fidelity and records where it came from, because an edited copy of a \texttt{verbatim} listing is no longer verbatim; the contributor must say again what it is. There is no sign-in, because a static site cannot complete GitHub's OAuth exchange without a server that holds the client secret \citep{githubOAuth}; that is a deliberate trade of convenience for the absence of a server.

\paragraph{Labelling an issue for a coding agent.} The fourth route, designed but not yet configured at the time of writing, hands transcription to an agent. A contributor opens an issue with the source: a scan of the page, or a reference and a pasted listing. A maintainer adds the \texttt{jules} label, and Jules \citep{jules}, Google's asynchronous coding agent, picks up the issue, reads the repository's standards in \texttt{AGENTS.md}, transcribes the listing and its metadata into the archive's files, runs the tests, and opens a pull request. Its limits are part of the design. The agent does the clerical work; it does not choose the fidelity, which comes from the contributor or is confirmed by the reviewer against the page. And a transcription from a scan is exactly where an undetected error enters an archive, so for this route the reviewer's comparison of the listing with the page is mandatory rather than advisable. The first real uses of the route, and any errors the reviewer caught, are to be reported before submission (Table~\ref{tab:prereq}).

\section{Building the software with an LLM coding agent}
\label{sec:llm}

Elsevier's policy requires that the use of AI tools in the research process be described in the methods, with the tool, its version and its developer \citep{elsevierAI}. This section does that, and tries to do more: to give a reader enough to judge how far to trust code that they did not see a person write.

\paragraph{Tools.} The software was built with Claude Code \citep{claudeCode}, Anthropic's agentic coding tool, running the model Claude Opus~5 (\texttt{claude-opus-5}), in September 2026, from the author's editor. The agent read and edited files, ran commands in the repository's container, and opened pull requests through the GitHub command-line tool. Jules appears in this paper only as a contribution route (Section~\ref{sec:contributing}); it was not used to build the software.

\paragraph{Division of labour.} The author set the requirements and made every design decision; the agent proposed designs, wrote the code, the tests and the documentation, ran the checks and opened the pull requests. The decisions that stayed with the author are the ones that shape the archive: that scanned diagrams are published only with their rights recorded; that contributions arrive through an issue form rather than through an OAuth service with a server behind it; that the archive is kept out of the workspace; and the layout of the interface, which was revised from a marked-up screenshot. The agent was not permitted to merge its own work. Every change reached the main branch through a pull request that the author reviewed and merged.

\paragraph{Controls.} Five controls were in place from the start (Table~\ref{tab:llm}). Written repository standards in \texttt{AGENTS.md} set out the architecture, the test-first rule, the dependency policy and the security rules; it is the same file Jules reads, so the two agents work to one standard. Tests were written before the code they test. Continuous integration runs the whole suite on every pull request, against both the development server and the production build, because a defect that appears only in the built bundle has already occurred once. Each task was done in its own git worktree, so that concurrent tasks could not read each other's build output. And every agent-assisted commit carries a co-author trailer, so the history records which changes the agent took part in. A sixth control was added while this paper was drafted, in response to the first failure below: the screenshots in this paper are the golden images of an end-to-end suite, compared pixel for pixel on every pull request, so a change that alters what the workbench looks like fails until its figures are regenerated on purpose.

\paragraph{What the controls caught.} The most useful evidence about a method is its failures, and each of the following is drawn from the repository's history. (a) Components' style rules leaked into one another, because the framework scopes only the host selector, so that one panel's \texttt{.empty} rule restyled another's; no test failed, and the leak was found by inspecting screenshots. (b) The issue-form parser attached the text of an unrelated section of the form to the diagram's rights statement; a dry run of the workflow against a synthetic issue found it before deployment, and a test now checks that every label in the form is either read or deliberately ignored. (c) A workflow used an expression context that is unavailable where it was used; a workflow linter found it. (d) An end-to-end test failed intermittently and the agent could not find the cause; it reported the failure in the pull request, with what it had tried, instead of suppressing the test. (e) The agent could not verify whether GitHub prefills an issue form's dropdowns from a URL, and flagged the behaviour as unverified rather than asserting it; the workspace lists the dropdown values in its submit dialog as a fallback. (f) One of the archive's worked examples, written by the agent, cuts its inflow two time steps later than the message it prints says. Every test passed; the error surfaced only when the validation in Section~\ref{sec:validation} compared the listing with its exact solution. (g) The agent wrote the workbench's screen to round a point half-way between two pixels upward, and recorded in the code that how the PC rounded a half had not been verified; the comparison with an emulator of the original machine (Section~\ref{sec:validation}) found that it rounds to even, which moves \oracleScreenDiffering{} pixels of one published listing's screen. The pattern across the seven is that the agent was reliable where a check existed and candid where one did not. That places the burden of quality on designing checks, which is where the human effort in this project went.

\paragraph{Limits and threats.} Co-author trailers attribute commits, not lines, so the agent's share of the code is known only coarsely: it took part in every commit except the repository's initial one. The process cannot be reproduced exactly, because the model is not deterministic and will be superseded; what is reproducible is the artefact, its tests and its history. Review is the bottleneck, and a single reviewer is a single point of failure. The interpreter is the component in which an undetected error would do the most harm, since every archived program depends on it, which is why it carries the analytical checks in Section~\ref{sec:validation} and why agreement with output printed in the sources is the validation that matters most. These observations are consistent with the software-engineering literature on LLM coding agents, which finds them capable on well-specified tasks with executable checks and much less reliable without them \citep{chen2021,jimenez2024} \verify{} (check that this characterisation fairly represents both papers).

\section{Validation}
\label{sec:validation}

Three kinds of evidence bear on whether the archive can be trusted: agreement with analytical results and agreement with the original machines' arithmetic, which test the interpreter, and agreement with output printed in the sources, which tests the archive. The first two are reported here; the third is decisive and depends on transcriptions that do not yet exist.

\paragraph{Against analytical results.} The three simulation models in the archive have exact solutions. The charge-and-discharge model is $\mathrm{d}Q/\mathrm{d}t = J - K_1Q$, with $Q(t) = (J/K_1)(1-e^{-K_1t})$. The logistic-growth model is $\mathrm{d}Q/\mathrm{d}t = K_1Q(S_T - Q) - K_2Q$, which is logistic growth with rate $r = K_1S_T - K_2$ and ceiling $C = S_T - K_2/K_1$, so that $Q(t) = C/[1 + ((C-Q_0)/Q_0)e^{-rt}]$. The two-tanks model is a linear system, $\mathrm{d}Q_1/\mathrm{d}t = J - K_1Q_1$ and $\mathrm{d}Q_2/\mathrm{d}t = K_1Q_1 - K_2Q_2$, with its inflow switched off part way through, and has a closed-form solution in each phase. Each listing integrates its model by forward Euler, so each run can be compared with two references: the listing's own Euler recurrence, computed independently in the same order of operations, and the exact solution. The first comparison tests the interpreter; the second measures the listing's method.

The comparison is a unit test in the repository (\texttt{src/basic/validation.test.ts}), which runs each archived listing through the interpreter, recovers its table with the same code the workbench uses to plot it, and prints the figures in Table~\ref{tab:validation}. On every row of every table, the interpreter's output agrees with the recurrence to within the rounding of \texttt{PRINT}, which prints six decimal places: no difference exceeds half a unit in the last printed place. The remaining differences from the exact solutions are the listings' first-order time step, and they are of the expected size: under one per cent of the peak for the two linear models, and seven per cent for the logistic model, whose growth rate times the step, $r\Delta t = 0.19$, is the coarsest of the three.

The comparison also found an error. The two-tanks listing prints ``inflow cut off at T=40'', and its exact solution with the inflow cut at $t=40$ differs from its run by 7.3 per cent of the peak, ten times more than the method explains. The cause is the listing, not the interpreter. \texttt{IF T > 40 THEN LET J = 0} is executed after the storages are updated, so the step that begins at $T = 40.25$ still uses the old inflow, and the inflow actually stops at $t = 40.5$. With the cut placed there, the difference falls to 0.7 per cent, in line with the other linear model. The listing is a worked example written for the archive, not a published one, so the error is ours; but it is precisely the kind of discrepancy that a published listing can contain, that no reading of the plot would reveal, and that only a comparison against an independent reference exposes. It is recorded as an open item in Table~\ref{tab:prereq}, to be resolved on the record rather than silently.

\paragraph{Against the original machine's arithmetic.} The interpreter computes in IEEE-754 double precision. GW-BASIC and BASICA, the dialects of Odum's later listings, compute by default in single precision, in Microsoft Binary Format, to about seven significant digits. A difference between a run and a published figure could therefore come from the interpreter rather than the listing, and the archive would then blame the source for it. To find out whether it does, we ran one published listing in both: Table~3 of \citet{odum1989}, a model of a developing economy that integrates four storages for \oracleSteps{} Euler steps and switches a flow off when one of them passes a threshold (\texttt{IF D > 30 THEN IV = 0}). The reference is PC-BASIC \citep{pcbasic}, an independent emulator of GW-BASIC that reproduces its number format. Each run printed the listing's state at every step: PC-BASIC in its default single precision and in double, the interpreter as it is and with single precision emulated (Table~\ref{tab:oracle}). The listing was read from a scan and has not yet been checked line by line against the page, but a misread coefficient changes both runs alike, so it does not weaken a comparison of the two.

Precision does not reach the figure. Single- and double-precision runs differ by at most \oracleSingleDoubleMaxRel{} relative, largest in the storage the listing holds at a floor of 0.0001, and no plotted point moves by more than \oracleSingleDoubleMaxPx{} of a pixel: in every pair of runs, every point of the four plotted series falls on the same screen pixel, and the threshold is crossed on step \oracleThresholdStep{} ($T = \oracleThresholdT$) in all of them. PC-BASIC in double precision agrees with the interpreter to \oracleDoubleMaxRel{}, so nothing but precision separates the two, and the statements the listing uses have no conformance defect. One subtlety mattered: declaring every variable double (\texttt{DEFDBL}) does not make a GW-BASIC run double-precision, because its literals are still read in single precision; the double run needed a type suffix on every constant. Emulating single precision with IEEE single brings the interpreter closer, but not to identity: \oracleBitIdenticalEvery{} of \oracleSteps{} steps agree bit for bit, because the Microsoft format rounds differently in the last place, and replaying one step at a time from PC-BASIC's exact state shows the two parting within a single step in \oracleReplayDiffering{} of \oracleReplaySteps{}. No figure drawn at screen resolution can show that difference.

Comparing screens rather than numbers found a difference that the numbers could not. PC-BASIC's screen, saved from its emulated video memory, differs from the workbench's in \oracleScreenDiffering{} of \oracleScreenPixels{} pixels (Figure~\ref{fig:oracle}). Emulating single precision leaves the count unchanged, so the cause is not arithmetic but rounding: a coordinate exactly half-way between two pixels goes to the even one in PC-BASIC and upward in the workbench, and Table~3's time axis, advancing half a unit per step, lands on such a half at every other step. With ties rounded to even, the two screens are identical. The workbench's rasteriser had recorded its rounding of halves as unverified; this comparison verified it, and it is corrected before any reproduced figure is compared with a published one (Table~\ref{tab:prereq}). PC-BASIC is itself an emulation, so what is shown is agreement with PC-BASIC; where it and the published source of GW-BASIC \citep{gwbasic} disagree, the source decides.

The comparison is an attestation that a reader can repeat. \texttt{make attest} rebuilds the pinned reference (PC-BASIC \oraclePcbasicVersion{} on Python \oraclePythonVersion{}, with Node \oracleNodeVersion{} for the interpreter, each container image pinned by digest), repeats every run from the listing, and checks every result byte for byte against a recorded checksum. The numbers in this section, Table~\ref{tab:oracle} and Figure~\ref{fig:oracle} are generated by it, and it fails if a change to the interpreter moves any of them, or if a claim made in this section stops holding.

\paragraph{Against output printed in the sources.} Where a book prints a program's output, as a table or a graph, the \texttt{verbatim} transcription must reproduce it. \section{Discussion}
\label{sec:discussion}

\paragraph{What running the listings makes possible.} The most direct use is to check a published model against its own claims: whether the listing, run as printed, produces the behaviour the text describes and the figure shows. Section~\ref{sec:validation} shows on a small scale how such a check can find something that reading cannot. A second is teaching with the originals, so that a student meets the model in the form its author gave it, and can change a coefficient and see what happens, as the listings were meant to be used. A third is comparing a listing with its diagram. The two were published as descriptions of the same model, and they need not agree; where they differ, one of them is wrong. This is also the bridge to the companion work: \texttt{energese} draws Energy Systems Language diagrams from a model file, and the GSSK kernel simulates from the same file \verify{} (cite both), so that a diagram and its simulation can no longer drift apart. An archive of the published pairs is a test set for that approach.

\paragraph{Fidelity as a general idea.} Recording how close an executable artefact is to the published one is not specific to BASIC or to Odum. Any collection of re-implementations, ports or transcriptions of published models faces the same question, and answers it, if at all, in prose. We suggest that fidelity belongs beside the FAIR principles for research software \citep{wilkinson2016,barker2022} as a recorded, controlled property: a small vocabulary with no default, chosen by a person, and enforced by the build. The four levels used here are a starting point, not a standard, and the useful part is less the vocabulary than the rule that a copy is never silently promoted to an original.

\paragraph{Figures, copyright and fair dealing.} The diagrams are someone's work. The easy course, for an archive like this one, is to reproduce them and hope; the resulting collection embodies a rights decision, but nobody made it and nobody can find it. The design here makes the decision explicit, per figure, recorded in the sidecar, reviewed with the rest of the contribution, and visible to every reader beside the image. The archive does not decide for anyone whether a particular reproduction is lawful: a contributor asserts a basis, a reviewer accepts or questions it, and the record says which. A basis can be revised, and a figure removed, if a rights holder objects, and the record makes it possible to find every figure from a given source when that happens. The wording of the fair-use and fair-dealing basis is to be checked with a copyright adviser before submission \verify.

\paragraph{Agents as contributors to scholarly archives.} Sections~\ref{sec:contributing} and~\ref{sec:llm} describe agents in two roles with different risks. As a builder, an agent's errors are errors in code, and tests can catch them; the history in Section~\ref{sec:llm} suggests they mostly do, where the tests exist. As a transcriber, an agent's errors are errors of fact about a page, and no test can catch a mistyped coefficient that still produces a plausible curve; only a person reading the page can. The archive's rules, that fidelity has no default, that review is mandatory, and that every file carries its provenance, are what make an agent's contribution acceptable. They would be as necessary without agents, since a person transcribing from a book makes the same errors; agents make the rules' purpose easier to see.

\paragraph{Limitations.} The interpreter covers the Commodore-era core but not yet the graphics and structured statements of the later listings, so many published programs will not run until it does. The plotting heuristic finds tables, not screen graphics. It plots every series against one axis, so a flow in the tens beside a storage in the thousands reads as nearly flat: that is the true relationship between them, but it hides the small series' shape, which then has to be read from the printed table. There is no sign-in, so the workspace cannot submit on a contributor's behalf and every submission passes through GitHub; the archive depends on GitHub for contribution, though not for use, since the site is static and the archive is plain files that any server can host. Interpreter arithmetic is double precision where GW-BASIC's is single. For the one listing compared with an emulator of the original machine (Section~\ref{sec:validation}) this moves no plotted pixel, but it can change the last printed digits, and one listing is not all of them. And the project has a single maintainer, which is the limitation that the design, built to outlive its authors, is meant to mitigate but cannot remove.

\section{Conclusions}
\label{sec:conclusions}

Odum BASIC Simulations makes the simulation listings of systems ecology runnable again, in a browser, without rewriting them. Each program is archived with a machine-checked record of where it came from, how faithful it is to the page, and on what basis its diagram is reproduced; the build refuses a program whose record is incomplete. Contributors can add programs from the browser, through a form, by pull request or, once configured, through a coding agent, and every route ends in the same validation and a person's review. The software was built by an LLM coding agent under test-first human review, and its record shows the method working where checks existed, with the checks rather than the agent carrying the weight. The interpreter reproduces the arithmetic of the three simulation listings in the archive to the precision they print, and comparing them with their exact solutions found an error that no test had.

What the archive needs now is what software cannot supply: transcriptions of published listings, with their citations; rights decisions for their figures; and reports of listings that do not yet run, which are the interpreter's to-do list. The archive is at \url{https://energese-project.github.io/Odum-basic-simulations/}, and its archived release at [DOI to mint].
