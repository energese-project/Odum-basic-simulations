\begin{abstract}
A simulation is an experiment, and an experiment that cannot be repeated is not yet evidence. H.T. Odum and his colleagues published many of their ecological simulation models as BASIC listings: short numbered programs, printed beside an Energy Systems Language diagram, meant to be typed in and run. Disclosure was complete --- the method was printed in full, in executable form --- and the results are nonetheless no longer repeatable, because the machines and language implementations those listings addressed have gone. Publishing the source, which is the remedy usually prescribed for irreproducible computational work, was therefore necessary but not sufficient: a program is repeatable only for as long as something can still run it. Odum BASIC Simulations is an open archive and browser workbench in which these listings run unaltered, restoring the runtime rather than the source. A BASIC interpreter written for the purpose runs in the browser: the table a program prints is recovered and plotted, with the printed output kept visible beside the plot, and a listing that draws on the screen instead of printing is shown as the screen it drew. Every program is stored with a machine-checked provenance record: a citation in BibLaTeX form, a declared fidelity to the published listing (verbatim, corrected, adapted or original) and, where available, the program's diagram with the rights under which it is reproduced. The build refuses any program whose record is incomplete. Programs can be contributed as a pull request, through a GitHub issue form processed by an automated workflow, from an in-browser workspace that fills in that form, or by labelling an issue for a coding agent, which transcribes the source into archive files for human review. The software itself was built largely by an LLM coding agent working under human direction, test-first, against written repository standards, with every change reviewed and merged by a person; that process is described here with its controls and the failures they caught. Three kinds of evidence are reported. For three mini-models the interpreter reproduces each listing's own Euler arithmetic on every printed row to within the rounding of its number format ($5\times10^{-7}$), and comparing those runs with the exact solutions exposed a timing error in one of the archive's own worked examples. Running a published listing against an emulator of the machine it was written for shows that the interpreter's double-precision arithmetic, where the original was single, moves no plotted point by more than $7\times10^{-5}$ of a pixel; comparing the screens rather than the numbers found instead a difference in how a coordinate half-way between two pixels is rounded, which the published source of GW-BASIC, not the emulator, settled. That comparison is packaged as an attestation any reader can rerun. The third kind, agreement with output printed in the sources, awaits transcriptions the archive does not yet hold. What the archive supplies is not a better model but a repeatable one: a published simulation that can be re-executed, inspected and disagreed with. The archive is openly available at \url{https://energese-project.github.io/Odum-basic-simulations/}.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Howard T. Odum and his colleagues did not only describe their models of ecological and economic systems; they printed them. Across the teaching and research books of the 1980s and 1990s a model is typically given twice, once as an Energy Systems Language diagram and once as a short BASIC listing that implements it \citep{odum1983,odumMinimodels,odumOdum2000}. The practice outlasted the machines that occasioned it: the last of those books still teaches BASIC programming in an appendix, and ships a CD-ROM carrying QuickBASIC and Extend versions of its minimodels beside the printed text \citep{odumOdum2000}. The listing was meant to be used. A student could type it into a microcomputer, run it, change a coefficient and run it again, and in doing so learn what the diagram meant as a set of differential equations. Few forms of publication in ecology are as concrete: the model is not described in prose and left for the reader to reconstruct, it is handed over whole, in a form that can be executed.

That form has not aged well. The machines the listings were written for are museum pieces, the dialects of BASIC they used have drifted apart and then out of use, and no current operating system ships an interpreter for any of them. A listing on paper is now a model that cannot be run, and a model that cannot be run cannot be checked against its own claims, compared with another model, or reused as the starting point for a new one.

What is lost when that happens is repeatability, and repeatability is not a convenience. A simulation is the instrument through which a systems-ecology model makes a quantitative claim: that a storage crests at a particular time, that a policy changes a trajectory, that one design outcompetes another. Such a claim is scientific in the ordinary sense only if someone other than its author can run the same procedure and obtain the same result, and the published listing was precisely the author's offer that they should. Computational science has largely diagnosed its own reproducibility problem as one of disclosure: results rest on code that is described in prose but never released, so the remedy is to publish the program \citep{ince2012,peng2011}. Ecological modelling has a strong version of the same instinct in its description standards, of which the ODD protocol is the most widely adopted \citep{grimm2010}.

Odum's listings are the awkward case for that diagnosis, because disclosure was already complete. The program was printed in full, in executable form, beside the diagram it implemented; nothing was withheld, and no description stands between the reader and the procedure. The results are irreproducible anyway. Publishing the source turns out to be necessary and not sufficient: a program is repeatable only for as long as some machine will still execute it, and it is the execution environment, not the source, that decayed. Retyping a listing into a modern language recovers execution at the cost of the thing being tested, since it produces a new program whose relationship to the published one is unrecorded: every translation decision and every typing error is silent. This is the general problem that \citet{hinsen2019} calls software collapse, in an unusually pure form. The code survived, on paper, in full; everything it depended on did not.

Software engineering has a name for the mechanism, and it is worth borrowing, because it locates the fault correctly. \citet{parnas1994} distinguishes two causes of software aging, and the first is lack of movement: software ages when it is \emph{not} changed while the world around it is, so that excellent programs written decades ago would still compute correctly and nobody can any longer run them. The literature that grew from this studies code that does move. Its laws are stated for systems under continuing adaptation \citep{lehman1980}; its empirical methods date every line from a version-control history, whether at project scale \citep{robles2005} or element by element across billions of events \citep{spinellis2021}. A listing printed in a book sits outside all of it. It has no repository, no commits and no maintainers; it has never been modified, and the median source line in an actively developed project survives about two and a half years \citep{spinellis2021} where these lines have survived unaltered for three decades and more. \citet{robles2005} calls code whose authors have left the project orphaned, and measures the fraction; Odum's listings are the limit of that measure, orphaned in full and from the start. Nor did they decay in the technical sense, since decay describes evolving software that grows progressively harder to change \citep{eick2001} and these listings were never changed at all. They were abandoned by their surroundings while remaining exactly what they were.

This paper presents Odum BASIC Simulations, an open archive and browser workbench built to make those published simulations repeatable again. Its argument is that for computational work whose runtime has gone, restoring repeatability means supplying a new execution environment for the original artefact rather than a new artefact for the surviving environment, and that doing so honestly requires the relationship between artefact and page to be recorded as data. It makes four contributions. First, a reconstruction of the execution environment those listings addressed: an interpreter, written for the purpose, runs them as printed, recovers a plot from the numbers a listing prints and rebuilds the screen a listing draws, so that nothing has to be rewritten for a listing to be run and seen. Because the machines are gone, what that environment did has to be established from evidence rather than observed, and the paper states the order in which conflicting sources are allowed to settle a question, together with a case in which the order mattered. Second, an archive in which each program's provenance is a machine-checked record rather than a comment: where the listing came from, how faithful it is to the page, and on what basis its diagram is reproduced. The build refuses a program whose record is incomplete. Third, four contribution routes, from a pull request to an in-browser workspace, designed so that someone with the book and no programming background can add a program without lowering the bar it must pass. Fourth, an account of how the software was built, largely by a large language model (LLM) coding agent working under human direction, with the controls that were used and the failures they caught, and of how a second agent can serve as a transcription route.

Section~\ref{sec:background} places the work in the history of simulation in Odum's systems ecology and in current practice for research software. Section~\ref{sec:design} states the design principles and the decisions each one forced, and Section~\ref{sec:implementation} describes the interpreter, the workbench and the archive. Section~\ref{sec:contributing} describes the contribution routes, Section~\ref{sec:llm} the use of an LLM coding agent as method, and Section~\ref{sec:validation} the validation, including a comparison with an emulator of the original machine that a reader can repeat. Section~\ref{sec:discussion} discusses what the archive makes possible and where it falls short.

\section{Background: simulation in Odum's systems ecology}
\label{sec:background}

Odum's energy circuit language began as an analogy with electrical circuits, in which storages behave like capacitors and flows like currents driven by a potential \citep{odum1960}. Over the following decades it became a general notation for systems of any kind, with symbols for sources, storages, interactions, producers, consumers and heat sinks that carry definite dynamical meaning \citep{odum1972,odum1983,odum1994}. Simulation was part of the notation from the start. A diagram specifies a set of differential equations, one per storage, and those equations were run: first on analogue computers, patched together to mirror the diagram, and later as programs on the microcomputers that reached teaching laboratories in the 1980s. The language itself, and the problem of drawing it reproducibly, are the subject of the companion \texttt{energese} work \citep{energese}; this paper is concerned with running the models.

The medium in which those programs reached their readers was BASIC, and the choice was not incidental. BASIC was designed at Dartmouth for students who were not programmers \citep{kemenyKurtz1964}, and by the 1980s some dialect of it was built into almost every microcomputer a student could reach. That made it the natural language for a listing printed in a book: short enough to type in an afternoon, and runnable without a compiler. The listings share a recognisable shape. Coefficients and initial storages are set with \texttt{LET}; a \texttt{FOR} loop advances time in steps of \texttt{DT}; inside it each flow is computed from the current storages and each storage is updated by forward Euler integration; and a \texttt{PRINT} statement emits one row of a table per step, or, in the later material, screen graphics plot the trajectories as they are computed. Listing~\ref{lst:shape} shows the shape, taken from a worked example in the archive. Two families of dialect appear in the sources. The earlier material is written to the Commodore-era BASIC V2 core, and the later to the IBM PC's, with \texttt{SCREEN}, \texttt{PSET} and \texttt{LINE} drawing the trajectory on the screen instead of printing it: the listing printed as Table~3 of \citet{odum1989}, which this paper uses throughout, is of the second kind, and that article records that its runs were accelerated with QuickBASIC.

Nothing available today makes those listings repeatable in the sense Section~\ref{sec:intro} requires, although three kinds of work come close. Emulators of the original machines can run a listing, but they need ROM images that cannot be redistributed, and they run the machine rather than the model: the listing still has to be typed in, the output still scrolls past on an emulated screen, and nothing records where the listing came from. General system-dynamics environments such as Stella \citep{richmond1985}, Vensim \citep{vensim} and Insight Maker \citep{fortmannRoe2014} can express the same models, often more conveniently, but only by re-expressing them; the published artefact itself is never run, so it is never checked. Odum's own later teaching took this path: \citet{odumOdum2000} builds its models as Extend blocks, and supplies the minimodels on a CD-ROM as QuickBASIC and Extend files rather than as listings to be typed. A printed listing needs only a reader and a keyboard; a CD-ROM of binaries needs the operating system it was cut for, which is the same collapse arriving sooner. Re-presentations of the published exercises exist --- the minimodels of \citet{odumMinimodels} have been on the web in an authorised edition since 2007 \citep{ortega2007} --- but they reproduce the text of the exercise around the program rather than a program that runs, so the listing remains something to read. The third body of work is the one closest in spirit, and the distance between it and the present problem is worth setting out, because it shows what has to be done differently.

Software archaeology is the name the discipline gave itself after the workshop that convened around it in 2001, and the metaphor it trades on is a good one: the investigator confronts an artefact whose makers are unavailable and must recover their intentions from what they left behind \citep{huntThomas2002}. In practice the excavation is almost always conducted on a version-control repository. \citet{robles2005} calls this the macro-archaeological view and derives from it a set of indices --- the age of the code, the fraction of it whose authors have left, how far the system has drifted from the people who understand it --- each computed from the record of who last modified each line. \citet{spinellis2021} pursues the same evidence down to the individual line and token, tracking births and deaths across 3.3 billion lifetime events in 89 repositories and fitting survival distributions to the result. Both take as their subject matter something that changed, and both take as their evidence a record of the changing, automatically kept.

Neither condition holds here. A listing printed in a book has no repository, no commits and no maintainers; it was never modified, so there is nothing to date, and the question the indices answer --- how far has this code drifted from the people who wrote it --- has the same answer for every listing in the corpus. The artefact is not degraded at all. It is intact, complete and perfectly legible, and it cannot be run. What has been lost is not the code but the machinery that gave it meaning: the interpreter, its arithmetic, its screen, the conventions by which a statement became a pixel. The excavation that these listings require is therefore of a different object. It is the execution environment that has to be reconstructed, and the artefact itself is one of the surviving pieces of evidence about what that environment did, rather than the thing under investigation.

That shift changes the method as well as the object, and Section~\ref{sec:design} states the rule it imposes. Where a repository supplies provenance as a by-product, an excavation of a dead runtime has to assemble its evidence from independent and unequal sources --- a published standard, the released source of the original implementation, the manuals, an emulator written by someone else --- which disagree, and which therefore have to be ranked before they are consulted. Section~\ref{sec:validation} reports one such disagreement and how the ranking settled it. What is missing, then, is an archive in which the listings themselves run: one that reconstructs the environment rather than mining the artefact, and that records the provenance a repository would have kept, because here no repository ever did.

How such a record should be shaped is a question current practice for research software has partly answered. The FAIR principles, first stated for data \citep{wilkinson2016} and since adapted for research software \citep{barker2022}, ask that software be findable, accessible, interoperable and reusable, and the software citation principles ask that it be cited as a first-class research output \citep{smith2016}. Both apply here, and the archive is designed to meet them: every program has a stable URL, a machine-readable record and a citation. None of them, though, asks whether the artefact still runs, and a listing can satisfy every one of them while remaining unexecutable; reusability is assessed against the artefact, not against the environment it needs. But an archive of transcriptions raises a question those frameworks do not name, because they assume the software in question is the original. That property is called \emph{fidelity} here: how close the executable artefact is to the published one. A program that has been corrected, modernised or rewritten may be exactly as findable and as reusable as a verbatim transcription, and still mean something quite different as evidence of what was published.

\section{Design principles}
\label{sec:design}

Five principles shaped the archive. Each is stated below with the decision it forced, because a principle that forced nothing is decoration. This section is the paper's argument about how such an archive should be built; Section~\ref{sec:implementation} describes how this one was.

The first principle is that the listing is the product. When a published listing and the interpreter disagree, the interpreter changes. The alternative, editing listings until they run, would make every archived program a derivative whose differences from the page have to be tracked and trusted. Three decisions follow. Listings are not rewritten into a modern language. A program's results are taken as it chose to emit them --- a plot recovered from the text it prints, or the screen it drew reconstructed as the PC showed it (Section~\ref{sec:implementation}) --- rather than by requiring an output convention that no published listing follows. And a statement the interpreter does not yet support is a gap in the interpreter, recorded as work to do, not a reason to edit the source.

The second is that provenance is data, and that incomplete provenance is a build failure. A listing whose origin cannot be read looks authoritative and is not. So every program carries a structured record, and the site does not build if any record is missing a required field or is inconsistent. The central field is \emph{fidelity} (Table~\ref{tab:fidelity}), with four levels from \texttt{verbatim} to \texttt{original}. It has no default, because it changes what every other field means: a \texttt{verbatim} listing's errors are the book's, an \texttt{adapted} listing's are the adapter's. Fidelity is also the one field that no automated route may set. A person chooses it, having compared the listing with the page.

The third principle governs the excavation itself, and is the rule that the archaeology of a dead runtime forces on anyone who attempts it: where references disagree, a standard or the published source decides. What the original machines did can be read from several references, and they do not always agree. Historical disciplines meet this situation routinely and answer it by ranking sources before consulting them, so that the weight given to a piece of evidence is fixed by what kind of evidence it is rather than by what it happens to say. The same discipline is needed here, and for the same reason: without a fixed order, the reference that happens to be most convenient decides, and the reconstruction quietly becomes a record of which document the investigator reached for first. The order used here runs from the most authoritative to the least. First is a published standard, where one covers the behaviour; none covers the graphics of Odum's later listings, since the Minimal BASIC standard \citep{ecma55} has no graphics and \texttt{SCREEN}, \texttt{PSET} and \texttt{LINE} are Microsoft's. Next is the published source of the original implementation: Microsoft has released GW-BASIC's source under the MIT licence \citep{gwbasic}, so for that dialect what the PC did can be read rather than inferred. Then come the original manuals, and then an independent open-source emulator such as PC-BASIC \citep{pcbasic}, which is an excellent oracle but is itself a reconstruction, so its agreement is evidence and its disagreement a question for the source. A closed implementation whose source was never published, such as the QuickBASIC with which \citet{odum1989} accelerated its runs, enters only through its manual or a run that others can repeat, never through recollection. Two decisions follow. Where the emulator departs from the source, the interpreter follows the source, and the departure is recorded with its evidence as a known difference rather than copied; the first such entry is how a coordinate half-way between two pixels is rounded (Section~\ref{sec:validation}). And code is taken only where its licence allows: GW-BASIC's MIT routines may be ported, but PC-BASIC's GPL code is read only to find the cause of a difference, never copied.

The fourth principle is that the archive should be built to outlive its authors, which is the lesson of the collapse it exists to repair. Its value is realised over decades, long after any maintainer has moved on \citep{hinsen2019}. It is therefore a static site with no server, no database and no account system: a directory of files that any web server can host. It uses the browser platform first, with Web Components rather than a framework, and has two runtime dependencies, the Monaco editor and the Chart.js plotting library, both bundled into the site rather than fetched from a content-delivery network at run time, so that the site keeps working for as long as its files exist. The component base class is vendored into the repository rather than installed, for the same reason: a dependency that is present as source cannot be withdrawn. Build and test tooling is exempt from this rule because none of it ships: if the build tools disappeared, the built site would still run.

The fifth principle is to test first, and from the outside. Every change begins with a failing test. The tests are written against behaviour a user could observe, not against internal methods: interpreter tests run a BASIC listing and assert on what it printed, and archive tests are phrased as the mistakes a contributor could make, such as a missing citation or an undeclared image. Tests written this way survive a rewrite of the implementation, which matters here for a second reason. In Section~\ref{sec:llm} they are the main check on an implementation that the human author directed and reviewed but did not write line by line.

\section{Implementation}
\label{sec:implementation}

This section describes the software at the level a modeller needs in order to trust it and use it. Everything else is in the repository, which the paper cites.

At the centre of the system is the interpreter, which is about a thousand lines of TypeScript, written from scratch for this purpose: it emulates no processor and needs no ROM image, so it can be redistributed with the archive. It implements the core the listings rely on: \texttt{PRINT} with its comma and semicolon separators, \texttt{LET} (with the keyword optional), numeric and string variables, one- and two-dimensional arrays with \texttt{DIM}, \texttt{FOR}/\texttt{TO}/\texttt{STEP}/\texttt{NEXT}, \texttt{IF}/\texttt{THEN} with a line number or a statement, \texttt{GOTO}, \texttt{GOSUB}/\texttt{RETURN}, \texttt{INPUT}, \texttt{DATA}/\texttt{READ}/\texttt{RESTORE}, \texttt{REM}, \texttt{END}, \texttt{STOP}, several statements per line separated by colons, and the numeric and string functions including \texttt{EXP}, \texttt{LOG}, \texttt{SQR}, \texttt{INT} and \texttt{RND}. It also implements the graphics statements of the later PC listings, which is what lets them run at all: \texttt{SCREEN} modes 1 and 2, \texttt{COLOR}, \texttt{CLS}, \texttt{PSET}, \texttt{PRESET} and \texttt{LINE} with its \texttt{STEP}, \texttt{B} and \texttt{BF} forms, together with \texttt{CONT}, which a listing that runs in stages needs in order to go on after an \texttt{END}. A listing of that kind draws rather than prints, so the screen is reconstructed as the PC showed it (Section~\ref{sec:validation}), while every point is also kept in the coordinates the program computed, which is what the plot is read back from. The structured-control and formatting statements (\texttt{WHILE}/\texttt{WEND}, \texttt{DEF FN}, \texttt{ON}\ldots\texttt{GOTO}, \texttt{SELECT CASE}, \texttt{PRINT USING}, \texttt{LOCATE}) are not yet implemented; the editor highlights them in a separate style rather than as errors, so a listing that uses them reads as code waiting for the interpreter, which is what it is. Arithmetic in the TypeScript interpreter is IEEE-754 double precision, and its \texttt{PRINT} rounds a number to six decimal places; the C engine that now executes the listings computes in single precision, because \texttt{BAS\_Real} is C's \texttt{float}, and prints a single to seven significant digits as GW-BASIC did (Section~\ref{sec:validation}). The original machines used shorter floating-point formats and printed a different number of digits --- Commodore BASIC V2 holds a number in five bytes, a 32-bit significand and an 8-bit exponent, and prints up to nine significant digits, where GW-BASIC's default single precision carries about seven --- so a faithful interpreter reproduces a listing's model and arithmetic, not necessarily the last printed digit of the original run (Section~\ref{sec:validation}). The interpreter runs in a Web Worker, so a runaway program can be stopped without freezing the page. It knows nothing of the page: its only contact with the outside world is a set of callbacks for output and input, which is why the same code runs in the browser and under the unit tests.

Recovering a plot from a program that predates plotting libraries requires a convention, and the one adopted here is to read the table the program printed. Those listings that print rather than draw print a table, not a data file, so the plot is recovered from their output. The rule is exact and deliberately simple. A line is numeric if it has at least two fields, separated by tabs or spaces, and every field parses as a finite number. A run of consecutive numeric lines with the same number of fields is a table, and a change of width ends it; the longest table in the output is the one plotted. Its first column is the independent variable and each further column is a series. If the nearest non-blank line above the table has the same number of fields and is not numeric, it supplies the column names, which is the shape a \texttt{PRINT "T", "Q"} before the loop produces; otherwise the columns are numbered. This is a heuristic on purpose. Requiring an output convention would mean rewriting the published programs, which the first principle forbids, and when the heuristic finds nothing the program's output is still shown in full. The plot has one y axis, never two, so that no series can be made to look like another by rescaling, and the printed output always stays visible beside the chart: the plot is never the only reading of a run. The recovered table can be downloaded as CSV.

The interface that assembles these parts is the workbench, shown in Figure~\ref{fig:workbench} with the first mini-model after a run. A thin top bar holds the program picker and the run controls. The sidebar holds the explorer, which lists the archive and the reader's own programs with the fidelity of each, and the details of the selected program: its description, fidelity and what that means, its citation with a BibLaTeX export, and the rights under which its diagram is shown. The listing is in the editor; the diagram, the recovered plot and the printed output are beside it. Each program has a stable address (\texttt{?prg=} followed by its identifier), so a paper or a lecture can link to a model ready to run.

The archive itself is one directory, \texttt{programs/}, and it holds two kinds of entry. A standalone program is two files and optionally a third: the listing (\texttt{.bas}), a metadata sidecar (\texttt{.json}, Listing~\ref{lst:sidecar}), and a diagram image. A published work --- one article or book --- is a folder, \texttt{programs/<author\_title\_year>/}, holding one \texttt{source.json} that states the citation once and the rights every image cut from it is published under, and beneath it a folder per model: the listing, its record, the crops of the listing and the diagram as they were printed, and one recorded run per published figure. The two kinds exist because provenance attaches at different levels. A worked example written here has no source to state; a listing transcribed from an article shares its source, its rights and its page with every other listing in that article, and stating them once is what keeps them consistent. Three rules hold the folder form together: the folder name is derived from the citation and checked against it, so it doubles as a BibTeX key; a recorded run may replace whole numbered lines of the listing but never edit it in place, so that \texttt{verbatim} stays true and every departure from the page is a visible diff; and \texttt{original} is refused inside a work, because a work is by definition something that was published. There is no manifest to keep in step: the build finds the files, validates every record with the same functions the contribution routes use (\texttt{parseProgramMeta} for one record, \texttt{readCatalog} for the directory, \texttt{readWork} for a folder), and fails with a message naming the file and the field if any record is incomplete or inconsistent. The raw files are published beside the site at stable URLs, so that a citation can point at the listing itself rather than at a page that displays it, and the end-to-end tests check that every published listing is identical to the one the workbench runs.

Diagrams are handled separately from listings, because their reproduction raises a question that a program does not. The diagram is the other half of what Odum published, and usually the easier half to check a model against (Figure~\ref{fig:minimodel}). A diagram is archived only with its rights recorded (Table~\ref{tab:rights}): a basis, which like fidelity has no default, a written statement, and for anything not drawn for the archive a source and, where it applies, the figure and page. The build rejects an image that no sidecar declares, an image whose content does not match its file extension, and any image over 2~MB. SVG is refused outright, because an SVG opened directly from the site can run scripts. The argument for recording rights per figure is in Section~\ref{sec:discussion}.

\section{Contributing programs}
\label{sec:contributing}

The archive grows only if people who own the books can add to them, and most of those people are ecologists, not programmers. There are therefore four routes in, in order of decreasing technical demand (Table~\ref{tab:routes}, Figure~\ref{fig:routes}). The point of the design is that every route ends in the same validator and the same human review, so that lowering the barrier to contributing does not lower the bar a contribution must clear.

The first route is a pull request. A contributor who uses git adds the two or three files, or the folder of a published work, and opens a pull request. Continuous integration builds the catalogue, which validates every sidecar, and runs the full test suite; a maintainer reviews and merges.

The second route removes the need for git. A contributor with a GitHub account and no knowledge of git or JSON opens an ``Add a program'' issue, pastes the listing, types the citation into labelled fields, chooses the fidelity and, if there is a diagram, drags the image in. A workflow parses the issue, builds the files, and checks the whole archive with the build's own validator. If anything is wrong it comments on the issue with every problem at once, in the form's own words; editing the issue runs it again. When everything passes it opens a pull request that credits the contributor as co-author, and runs the full test suite on it. Two security properties matter, because the issue text is written by anyone. The issue text is never passed to a shell: it is read from the event payload by a script, and the only part of the issue that reaches a shell command is its number. And a diagram is downloaded only from GitHub's own attachment hosts, so the workflow cannot be made to fetch an arbitrary URL. A photograph of the source page can be attached for the reviewer; it stays in the issue and is not published, so a page image is never redistributed from the archive.

The third route removes the need to leave the workbench at all, since a contributor can write a program in it. ``My programs'' is a private area of the browser's own storage, the Origin Private File System, in which a program can be written, run and described, with the details panel acting as a form that is checked against the build's rules as the contributor types (Figure~\ref{fig:workspace}). \emph{Submit} then opens the issue form above, already filled in, so the workspace is a friendlier front end to the second route rather than a separate one. Two design decisions are worth stating. The archive itself is never copied into the workspace as a whole, because a copy would go stale when an entry is corrected upstream. And an individual archive program copied into the workspace loses its fidelity and records where it came from, because an edited copy of a \texttt{verbatim} listing is no longer verbatim; the contributor must say again what it is. There is no sign-in, because a static site cannot complete GitHub's OAuth exchange without a server that holds the client secret \citep{githubOAuth}; that is a deliberate trade of convenience for the absence of a server.

The fourth route, designed but not yet configured at the time of writing, hands transcription itself to an agent. A contributor opens an issue with the source: a scan of the page, or a reference and a pasted listing. A maintainer adds the \texttt{jules} label, and Jules \citep{jules}, Google's asynchronous coding agent, picks up the issue, reads the repository's standards in \texttt{AGENTS.md}, transcribes the listing and its metadata into the archive's files, runs the tests, and opens a pull request. Its limits are part of the design. The agent does the clerical work; it does not choose the fidelity, which comes from the contributor or is confirmed by the reviewer against the page. And a transcription from a scan is exactly where an undetected error enters an archive, so for this route the reviewer's comparison of the listing with the page is mandatory rather than advisable. The route is described here as designed rather than as demonstrated: at the time of writing it has not yet processed a contribution, so nothing is claimed about its error rate.

\section{Building the software with an LLM coding agent}
\label{sec:llm}

Elsevier's policy requires that the use of AI tools in the research process be described in the methods, with the tool, its version and its developer \citep{elsevierAI}. This section does that, and tries to do more: to give a reader enough to judge how far to trust code that they did not see a person write.

The question belongs to this paper rather than beside it. An archive whose purpose is to make published results repeatable is itself an instrument, and an instrument is only as good as the checks that can be run against it. That is the same standard the archive applies to the models it holds, turned on the software that runs them: what follows is offered not as a claim that an agent can be trusted, but as a record of which checks caught what, so that a reader can judge the instrument the way they would judge any other.

The tools are named first, as the policy requires. The software was built with Claude Code \citep{claudeCode}, Anthropic's agentic coding tool, running the model Claude Opus~5 (\texttt{claude-opus-5}), in September 2026, from the author's editor. The agent read and edited files, ran commands in the repository's container, and opened pull requests through the GitHub command-line tool. Jules appears in this paper only as a contribution route (Section~\ref{sec:contributing}); it was not used to build the software.

The division of labour was as follows. The author set the requirements and made every design decision; the agent proposed designs, wrote the code, the tests and the documentation, ran the checks and opened the pull requests. The decisions that stayed with the author are the ones that shape the archive: that scanned diagrams are published only with their rights recorded; that contributions arrive through an issue form rather than through an OAuth service with a server behind it; that the archive is kept out of the workspace; and the layout of the interface, which was revised from a marked-up screenshot. The agent was not permitted to merge its own work. Every change reached the main branch through a pull request that the author reviewed and merged.

Five controls were in place from the start (Table~\ref{tab:llm}). Written repository standards in \texttt{AGENTS.md} set out the architecture, the test-first rule, the dependency policy and the security rules; it is the same file Jules reads, so the two agents work to one standard. Tests were written before the code they test. Continuous integration runs the whole suite on every pull request, against both the development server and the production build, because a defect that appears only in the built bundle has already occurred once. Each task was done in its own git worktree, so that concurrent tasks could not read each other's build output. And every agent-assisted commit carries a co-author trailer, so the history records which changes the agent took part in. A sixth control was added while this paper was drafted, in response to the first failure below: the screenshots in this paper are the golden images of an end-to-end suite, compared pixel for pixel on every pull request, so a change that alters what the workbench looks like fails until its figures are regenerated on purpose.

What those controls caught is the more informative record, since the most useful evidence about a method is its failures, and each of the following is drawn from the repository's history. (a) Components' style rules leaked into one another, because the framework scopes only the host selector, so that one panel's \texttt{.empty} rule restyled another's; no test failed, and the leak was found by inspecting screenshots. (b) The issue-form parser attached the text of an unrelated section of the form to the diagram's rights statement; a dry run of the workflow against a synthetic issue found it before deployment, and a test now checks that every label in the form is either read or deliberately ignored. (c) A workflow used an expression context that is unavailable where it was used; a workflow linter found it. (d) An end-to-end test failed intermittently and the agent could not find the cause; it reported the failure in the pull request, with what it had tried, instead of suppressing the test. (e) The agent could not verify whether GitHub prefills an issue form's dropdowns from a URL, and flagged the behaviour as unverified rather than asserting it; the workspace lists the dropdown values in its submit dialog as a fallback. (f) One of the archive's worked examples, written by the agent, cuts its inflow two time steps later than the message it prints says. Every test passed; the error surfaced only when the validation in Section~\ref{sec:validation} compared the listing with its exact solution. (g) The agent wrote the workbench's screen to round a point half-way between two pixels upward, and recorded in the code that how the PC rounded a half had not been verified. The comparison with an emulator of the original machine (Section~\ref{sec:validation}) found that the emulator rounds such a point to even, which moves \oracleScreenDiffering{} pixels of one published listing's screen, and the agent's first reading, written into the project's plan, was that the workbench should follow the emulator. Before the change was made, the rule the comparison works under (Section~\ref{sec:design}), that the published source of GW-BASIC decides where the emulator is in doubt, showed the reverse: GW-BASIC rounds a half away from zero, so the workbench was already right for every point on the screen, and the emulator was not. Only negative halves, which the workbench rounded towards zero, needed correcting. The pattern across the seven is that the agent was reliable where a check existed and candid where one did not. That places the burden of quality on designing checks, which is where the human effort in this project went --- and it is the reason the validation in Section~\ref{sec:validation} is packaged as an attestation a reader can rerun rather than as a table of numbers to be taken on trust. An archive that asks scientists to rely on it has no better claim on their confidence than the checks they can repeat for themselves.

Several limits qualify all of this. Co-author trailers attribute commits, not lines, so the agent's share of the code is known only coarsely: it took part in every commit except the repository's initial one. The process cannot be reproduced exactly, because the model is not deterministic and will be superseded; what is reproducible is the artefact, its tests and its history. Review is the bottleneck, and a single reviewer is a single point of failure. The interpreter is the component in which an undetected error would do the most harm, since every archived program depends on it, which is why it carries the analytical checks in Section~\ref{sec:validation} and why agreement with output printed in the sources is the validation that matters most. None of this is peculiar to this project: the dependence on checks that the failures above display is the pattern the benchmark literature reports. Models evaluated on self-contained functions with a specification and a test suite succeed at a substantial rate \citep{chen2021}; the same models turned on real issues in real repositories, where the task is under-specified and the relevant code has to be found first, succeed at a far lower one \citep{jimenez2024}. Neither benchmark measures what this project relied on --- an agent working to written standards under a human reviewer --- but both point the same way: the executable check, not the model, is what the result rests on.

\section{Validation}
\label{sec:validation}

Three kinds of evidence bear on whether the archive can be trusted: agreement with analytical results and agreement with the original machines' arithmetic, which test the interpreter, and agreement with output printed in the sources, which tests the archive. The first two are reported here; the third is decisive and depends on transcriptions that do not yet exist.

The first kind of evidence is agreement with analytical results, which is available because the three simulation models in the archive have exact solutions. The charge-and-discharge model is $\mathrm{d}Q/\mathrm{d}t = J - K_1Q$, with $Q(t) = (J/K_1)(1-e^{-K_1t})$. The logistic-growth model is $\mathrm{d}Q/\mathrm{d}t = K_1Q(S_T - Q) - K_2Q$, which is logistic growth with rate $r = K_1S_T - K_2$ and ceiling $C = S_T - K_2/K_1$, so that $Q(t) = C/[1 + ((C-Q_0)/Q_0)e^{-rt}]$. The two-tanks model is a linear system, $\mathrm{d}Q_1/\mathrm{d}t = J - K_1Q_1$ and $\mathrm{d}Q_2/\mathrm{d}t = K_1Q_1 - K_2Q_2$, with its inflow switched off part way through, and has a closed-form solution in each phase. Each listing integrates its model by forward Euler, so each run can be compared with two references: the listing's own Euler recurrence, computed independently in the same order of operations, and the exact solution. The first comparison tests the interpreter; the second measures the listing's method.

The comparison is a unit test in the repository (\texttt{src/basic/validation.test.ts}), which runs each archived listing through the engine the site executes, recovers its table with the same code the workbench uses to plot it, and prints the figures in Table~\ref{tab:validation}. The recurrence is computed in single precision, because the engine is: \texttt{BAS\_Real} is C's \texttt{float}, so every operation rounds to single because that is what the type does, and a double-precision reference would measure the distance between the machine and an idealisation of it rather than the fidelity of the run. On every row of every table, the engine's output agrees with that recurrence to within the rounding of \texttt{PRINT}, which gives a single seven significant digits: no difference exceeds half a unit in the last printed place. That threshold is relative rather than absolute --- seven significant figures quantise $997.8776$ at $10^{-4}$ and $.8560597$ at $10^{-7}$ --- and its worst case is $5\times10^{-7}$ of the value, which is where the tolerance in the table comes from. The remaining differences from the exact solutions are the listings' first-order time step, and they are of the expected size: under one per cent of the peak for the two linear models, and seven per cent for the logistic model, whose growth rate times the step, $r\Delta t = 0.19$, is the coarsest of the three.

The comparison also found an error. The two-tanks listing prints ``inflow cut off at T=40'', and its exact solution with the inflow cut at $t=40$ differs from its run by 7.3 per cent of the peak, ten times more than the method explains. The cause is the listing, not the interpreter. \texttt{IF T > 40 THEN LET J = 0} is executed after the storages are updated, so the step that begins at $T = 40.25$ still uses the old inflow, and the inflow actually stops at $t = 40.5$. With the cut placed there, the difference falls to 0.7 per cent, in line with the other linear model. The listing is a worked example written for the archive, not a published one, so the error belongs to the archive rather than to a source; but it is precisely the kind of discrepancy that a published listing can contain, that no reading of the plot would reveal, and that only a comparison against an independent reference exposes. It is left in the archive as it was written, and recorded as a known defect of that example, so that the disagreement between a listing and its own printed message stays visible rather than being quietly corrected away.

The second kind of evidence concerns the arithmetic of the original machine, and it is here that the excavation described in Section~\ref{sec:background} is actually carried out. The interpreter computes in IEEE-754 double precision. GW-BASIC and BASICA, the dialects of Odum's later listings, compute by default in single precision, in Microsoft Binary Format, to about seven significant digits. A difference between a run and a published figure could therefore come from the interpreter rather than the listing, and the archive would then blame the source for it. To find out whether it does, one published listing was run in both: Table~3 of \citet{odum1989}, a model of a developing economy that integrates four storages for \oracleSteps{} Euler steps and switches a flow off when one of them passes a threshold (\texttt{IF D > 30 THEN IV = 0}). The reference is PC-BASIC \citep{pcbasic}, an independent emulator of GW-BASIC that reproduces its number format. Each run printed the listing's state at every step: PC-BASIC in its default single precision and in double, the interpreter as it is and with single precision emulated (Table~\ref{tab:oracle}). The listing was read from a scan and has not yet been checked line by line against the page, but a misread coefficient changes both runs alike, so it does not weaken a comparison of the two.

Precision does not reach the figure. Single- and double-precision runs differ by at most \oracleSingleDoubleMaxRel{} relative, largest in the storage the listing holds at a floor of 0.0001, and no plotted point moves by more than \oracleSingleDoubleMaxPx{} of a pixel: in every pair of runs, every point of the four plotted series falls on the same screen pixel, and the threshold is crossed on step \oracleThresholdStep{} ($T = \oracleThresholdT$) in all of them. PC-BASIC in double precision agrees with the interpreter to \oracleDoubleMaxRel{}, so nothing but precision separates the two, and the statements the listing uses have no conformance defect. One subtlety mattered: declaring every variable double (\texttt{DEFDBL}) does not make a GW-BASIC run double-precision, because its literals are still read in single precision; the double run needed a type suffix on every constant. Emulating single precision with IEEE single brings the interpreter closer, but not to identity: \oracleBitIdenticalEvery{} of \oracleSteps{} steps agree bit for bit, because the Microsoft format rounds differently in the last place, and replaying one step at a time from PC-BASIC's exact state shows the two parting within a single step in \oracleReplayDiffering{} of \oracleReplaySteps{}. No figure drawn at screen resolution can show that difference.

Comparing screens rather than numbers found a difference that the numbers could not. PC-BASIC's screen, saved from its emulated video memory, differs from the workbench's in \oracleScreenDiffering{} of \oracleScreenPixels{} pixels (Figure~\ref{fig:oracle}). Emulating single precision leaves the count unchanged, so the cause is not arithmetic but rounding: Table~3's time axis, advancing half a unit per step, puts every other point exactly half-way between two pixels, and PC-BASIC's \texttt{PSET} sends such a point to the even pixel where the workbench sends it upward. With PC-BASIC's rule applied to the workbench's points, the two screens are identical. Which of the two rules was the PC's is not for the emulator to settle, and PC-BASIC does not agree with itself on it: its \texttt{PSET} puts a coordinate of \oracleProbeValue{} on pixel~\oracleProbePset{}, but its \texttt{CINT(\oracleProbeValue)} is \oracleProbeCint{}. In the published source of GW-BASIC \citep{gwbasic} the two are one routine. Every graphics coordinate is converted to an integer by the routine \texttt{CINT} uses, which rounds a half away from zero. The workbench's rounding was therefore already the PC's for every point on the screen, and PC-BASIC's is a departure of the emulator, which the archive records as a known difference rather than copies. The one correction the source called for was to negative halves, which the workbench rounded towards zero; such a point falls off the screen, or moves where a clipped line enters it, and none arises in Table~3. This is the point at which the ranking of sources stops being a methodological preamble and does some work. PC-BASIC is itself a reconstruction, built by reading the same machine this project is trying to read; treating its behaviour as the answer would be treating a secondary account as a primary one, and would have propagated a modern author's inference into an archive whose purpose is to record what was published. Agreement with it is evidence, not proof, and where it and the source of GW-BASIC disagree the source decides (Section~\ref{sec:design}), as it did here. Two further features of the episode are worth noting, because they are what makes the reconstruction checkable rather than merely argued. The disagreement was visible only because two independent reconstructions were run against each other and compared at the level of pixels, which no reading of either could have achieved; and the emulator's departure is retained in the archive as a recorded known difference rather than silently discarded, so that a later investigator with better evidence can reopen the question on the record. One question is left open by this: \citet{odum1989} reports that its runs were accelerated with QuickBASIC, a later and separately written implementation whose source Microsoft has not released, so whether it rounded a graphics coordinate as GW-BASIC did cannot be read and would have to be established from its manual or from a run that others can repeat.

The comparison is an attestation that a reader can repeat. \texttt{make attest} rebuilds the pinned reference (PC-BASIC \oraclePcbasicVersion{} on Python \oraclePythonVersion{}, with Node \oracleNodeVersion{} for the interpreter, each container image pinned by digest), repeats every run from the listing, and checks every result byte for byte against a recorded checksum. The numbers in this section, Table~\ref{tab:oracle} and Figure~\ref{fig:oracle} are generated by it, and it fails if a change to the interpreter moves any of them, or if a claim made in this section stops holding.

The third kind of evidence is agreement with output printed in the sources. Where a book prints a program's output, as a table or a graph, the \texttt{verbatim} transcription must reproduce it. This is the result that validates the archive rather than the arithmetic, and it is not yet available: it depends on \texttt{verbatim} transcriptions of published listings, which the archive does not yet hold. It will be reported per program, and every disagreement treated as a finding: a misprint in the book, a transcription error, or an interpreter defect, each resolved on the record through the \texttt{corrected} mechanism. Agreement is expected to the digits the source prints, not beyond, because the original machines' arithmetic and number formats differ from the interpreter's (Section~\ref{sec:implementation}).

The test suite is the supporting evidence for all three. At the commit recorded in Table~\ref{tab:llm} it held 218 unit tests, including interpreter tests that run a listing and assert on what it printed, and archive tests phrased as the mistakes a contributor could make; 48 end-to-end tests, each run against both the development server and the production build, including the check that every published listing is identical to the one the workbench runs; and three figure tests, which capture the screenshots in this paper from the production build and fail if the workbench stops looking like them.

\section{Discussion}
\label{sec:discussion}

The point of running the listings is that a published simulation becomes an experiment a reader can repeat. The most direct use is to check a model against its own claims: whether the listing, run as printed, produces the behaviour the text describes and the figure shows. That check is not hypothetical. Section~\ref{sec:validation} reports a worked example whose printed message disagrees with what it computes, found only because an independent reference could be run against it; the same disagreement in a published model would be invisible to any amount of reading. Repeatability is what converts a printed model from a description to be trusted into a claim that can be tested and, where necessary, contradicted. A second is teaching with the originals, so that a student meets the model in the form its author gave it, and can change a coefficient and see what happens, as the listings were meant to be used. A third is comparing a listing with its diagram. The two were published as descriptions of the same model, and they need not agree; where they differ, one of them is wrong. This is also the bridge to the companion work: \texttt{energese} draws Energy Systems Language diagrams from a model file \citep{energese}, and the GSSK kernel simulates from the same file \citep{gssk}, so that a diagram and its simulation can no longer drift apart. An archive of the published pairs is a test set for that approach.

The archaeology this required is worth separating from the archive it produced, because it is the part most likely to be needed again. Existing software archaeology excavates a program: the artefact is degraded, obscure or undocumented, and the investigator works to recover what its authors meant \citep{huntThomas2002}, in practice by mining the record of changes that a repository kept \citep{robles2005,spinellis2021}. The corpus considered here inverts every term of that description. The artefact is pristine and entirely documented --- it is a printed listing, set in type, beside a diagram explaining it --- and no record of changes exists because there were none. What is missing is everything around it. The excavation is therefore of the execution environment, and the listing is not the site but one of the finds.

That inversion has three methodological consequences, each visible in the preceding sections. Evidence must be ranked, because a dead runtime is attested by sources of unequal standing --- a standard, the released source of the original implementation, a manual, a modern emulator --- which disagree, and a reconstruction that consults them in whatever order they come to hand records the investigator's reading habits rather than the machine (Section~\ref{sec:design}). Reconstructions must be distinguished from sources, since an emulator is a secondary account written by someone else attempting the same recovery, so that its agreement is corroboration and its disagreement is a question rather than an answer; Section~\ref{sec:validation} reports a case where deferring to it would have written a modern inference into the archive. And disagreements must be retained rather than resolved away, because the evidence may improve: the departure found there is recorded as a known difference, with what was compared and what decided it, so that the finding can be reopened by someone who later reads the QuickBASIC manual this paper could not obtain.

None of this is peculiar to BASIC. Any computational result whose runtime has gone --- a model written for a discontinued solver, a pipeline built on an abandoned library, an analysis that ran only on a machine nobody now owns --- presents the same problem in the same shape, and the same three requirements follow. The conclusion drawn here is that such cases call for reconstruction of the environment, conducted as an evidential exercise and reported as one, rather than for the translation of the artefact into whatever is currently available; and that the discipline of saying which source decided a question is what separates the first from an educated guess.

Fidelity, the second of the archive's contributions, generalises beyond this corpus. Recording how close an executable artefact is to the published one is not specific to BASIC or to Odum. Any collection of re-implementations, ports or transcriptions of published models faces the same question, and answers it, if at all, in prose. It is a question the software-evolution literature never has to ask, because there the provenance of every line is a by-product of the version-control system that recorded it \citep{robles2005,spinellis2021}. Where the artefact arrived as ink on a page, no such record exists and none can be mined; it has to be asserted by a person and then enforced, which is what fidelity is. Fidelity belongs beside the FAIR principles for research software \citep{wilkinson2016,barker2022} as a recorded, controlled property: a small vocabulary with no default, chosen by a person, and enforced by the build. The four levels used here are a starting point, not a standard, and the useful part is less the vocabulary than the rule that a copy is never silently promoted to an original.

A third question, less tractable than either, concerns the figures. The diagrams are someone's work. The easy course, for an archive like this one, is to reproduce them and hope; the resulting collection embodies a rights decision, but nobody made it and nobody can find it. The design here makes the decision explicit, per figure, recorded in the sidecar, reviewed with the rest of the contribution, and visible to every reader beside the image. The archive does not decide for anyone whether a particular reproduction is lawful: a contributor asserts a basis, a reviewer accepts or questions it, and the record says which. A basis can be revised, and a figure removed, if a rights holder objects, and the record makes it possible to find every figure from a given source when that happens. Two limits should be stated plainly. The vocabulary in Table~\ref{tab:rights} is a record of an assertion, not a legal opinion, and \texttt{fair-use} in particular names a doctrine that differs between jurisdictions and is decided case by case; the archive records who claimed it and on what ground, which is the most a build can check. And the rights of the diagram are not the rights of the listing, which the archive treats separately, because a short program expressing a published equation and a drawing of it are not alike in what their reproduction requires.

The role of automated agents in an archive of this kind deserves separate comment, because Sections~\ref{sec:contributing} and~\ref{sec:llm} describe them in two roles with different risks. As a builder, an agent's errors are errors in code, and tests can catch them; the history in Section~\ref{sec:llm} suggests they mostly do, where the tests exist. As a transcriber, an agent's errors are errors of fact about a page, and no test can catch a mistyped coefficient that still produces a plausible curve; only a person reading the page can. The archive's rules, that fidelity has no default, that review is mandatory, and that every file carries its provenance, are what make an agent's contribution acceptable. They would be as necessary without agents, since a person transcribing from a book makes the same errors; agents make the rules' purpose easier to see.

Several limitations bound what has been claimed. The interpreter covers the core of both dialect families and the graphics statements the later listings draw with, but not their structured-control and formatting statements (\texttt{WHILE}/\texttt{WEND}, \texttt{DEF FN}, \texttt{ON}\ldots\texttt{GOTO}, \texttt{PRINT USING}), so some published programs will not run until it does. The plotting heuristic finds printed tables; a listing that draws instead of printing is shown as the screen it drew, and yields no series to plot. It plots every series against one axis, so a flow in the tens beside a storage in the thousands reads as nearly flat: that is the true relationship between them, but it hides the small series' shape, which then has to be read from the printed table. There is no sign-in, so the workspace cannot submit on a contributor's behalf and every submission passes through GitHub; the archive depends on GitHub for contribution, though not for use, since the site is static and the archive is plain files that any server can host. Interpreter arithmetic is double precision where GW-BASIC's is single. For the one listing compared with an emulator of the original machine (Section~\ref{sec:validation}) this moves no plotted pixel, but it can change the last printed digits, and one listing is not all of them. And the project has a single maintainer, which is the limitation that the design, built to outlive its authors, is meant to mitigate but cannot remove.

\section{Conclusions}
\label{sec:conclusions}

A published simulation is a scientific claim, and a claim that can no longer be executed can no longer be checked. Odum's listings lost their repeatability without losing a line of their source: the method stayed fully disclosed while the machines that could act on it disappeared, which is the case that publishing the code does not by itself address \citep{ince2012,parnas1994}. Odum BASIC Simulations makes the simulation listings of systems ecology runnable again, in a browser, without rewriting them. Each program is archived with a machine-checked record of where it came from, how faithful it is to the page, and on what basis its diagram is reproduced; the build refuses a program whose record is incomplete. Contributors can add programs from the browser, through a form, by pull request or, once configured, through a coding agent, and every route ends in the same validation and a person's review. The software was built by an LLM coding agent under test-first human review, and its record shows the method working where checks existed, with the checks rather than the agent carrying the weight. The interpreter reproduces the arithmetic of the three simulation listings in the archive to the precision they print; comparing them with their exact solutions found an error that no test had; and running a published listing beside an emulator of the machine it was written for showed that the difference in precision moves nothing that can be seen on a screen, while a difference that could be seen turned out to be the emulator's departure from the source it emulates, not the interpreter's.

The general lesson is modest and, it is argued here, transferable. Where a computational result has outlived its runtime, repeatability is recovered by rebuilding the environment around the original artefact rather than by rewriting the artefact for a surviving environment, and the difference between those two has to be recorded as data if the result is still to count as evidence about what was published. What the archive needs now is what software cannot supply: transcriptions of published listings, with their citations; rights decisions for their figures; and reports of listings that do not yet run, which are the interpreter's to-do list. The archive is at \url{https://energese-project.github.io/Odum-basic-simulations/}, and its archived release at [DOI to mint].
